왜 MQTT였나

집 안 네트워크의 기기에는 밖에서 직접 요청을 보낼 수 없습니다. 기기가 먼저 브로커에 접속해 구독해 두면, 웹이 보낸 명령이 브로커를 거쳐 도착합니다. 브라우저는 WebSocket으로, ESP32는 MQTT로 같은 브로커에 붙였습니다.

화면과 기기 상태 맞추기

명령 토픽과 상태 토픽을 나눴습니다. 버튼을 누르면 화면이 먼저 바뀌고, 기기가 보낸 상태가 도착하면 그 값으로 다시 맞춥니다. 브로커 연결 여부도 화면에 표시했습니다.

보안과 배포

브로커에 MQTT 인증을 걸고, 웹에는 JWT 로그인을 붙였습니다. 웹은 GitHub Actions로 배포했습니다.
다시 만든다면 · 기기가 꺼져 있으면 화면만 켜진 상태로 남을 수 있습니다. 일정 시간 안에 상태 응답이 없으면 "응답 없음"으로 되돌리는 처리가 필요합니다. 관제 화면이라면 이 부분이 가장 중요하다고 생각합니다. 또 이 프로젝트는 제어와 상태 피드백까지였고, 센서 값을 모아 시계열로 저장·시각화하는 일은 해 보지 못했습니다. 공개 저장소에는 웹 부분이 올라가 있습니다.

CAPD 산학과제 · 2인 팀 · 2026.04~06

복막투석 환자의 일일 기록을 의료진이 검토하고 AI가 후속 질문을 돕는 시스템입니다. 저는 FastAPI 백엔드, AI 파이프라인, GCP 인프라(Cloud Run 3개)를, 팀원은 프런트엔드를 맡았습니다(기여도 50:50).
  • LLM에 맡길 일을 나눔: LLM 하나에 수치 계산과 해석을 모두 맡겼다가 계산 오류가 반복돼, 계산은 Python이, 임상 해석은 Gemini가 맡도록 바꾸고 의학 가이드라인 RAG(1,012청크, pgvector)를 붙였습니다.
  • LLM 응답을 화면으로: 응답 생성 시간과 화면의 확인 주기가 맞지 않아 폴링을 SSE 스트리밍으로 바꾸고 팀원과 응답 형식을 다시 맞췄습니다.
  • 10주간 기능 80건 이상

SyncAI 개인 · 2026.05~10

팀원마다 AI를 다르게 써서 생기던 충돌에서 출발한 AI 협업 도구입니다.
  • 계획을 세우는 Supervisor 에이전트와 실행하는 Worker 에이전트를 분리
  • MCP로 서버와 로컬 PC를 연결해 채팅 명령으로 파일 수정, 외부 앱 연동
  • 민감한 작업은 실행 전에 사용자 승인을 받도록 설계
  • 커밋 321개, Fly.io 배포까지 했지만 시장 출시와 사용자 확보는 하지 못했습니다.
